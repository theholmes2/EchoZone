개인 영구 월드 기반 3D PvE 익스트랙션 게임 기획 정리
=====================================================

문서 버전
---------
초기 비동기 공유 월드 및 우선순위 점수 설계를 폐기하고, 하나의 월드를 한 명의 소유자가 보유하며 멀티플레이 시 다른 플레이어가 그 월드에 실시간으로 참가하는 구조로 개정했다.


1. 최종 핵심 방향
-----------------

장르:
"개인 영구 월드를 소유하고 필요할 때 다른 플레이어를 초대할 수 있는 3D PvE 익스트랙션 게임"

기본 구조:

- 맵은 하나다.
- 처음에는 싱글플레이로 개발한다.
- 각 플레이어는 자기만의 영구 월드 하나를 가진다.
- 문 파괴, 지뢰 설치, 시설 작동, 보스 체력, NPC 수리 같은 상태는 그 개인 월드에 저장된다.
- 싱글플레이에서는 월드 소유자 한 명만 접속하므로 플레이어 간 충돌이 없다.
- 추후 멀티플레이를 추가하면 월드 소유자가 호스트가 된다.
- 친구나 공개 참가자는 호스트의 월드에 들어와 같은 실시간 상태를 공유한다.
- 참가자가 만든 변화도 호스트 월드에 저장된다.
- 서버 하나가 모든 사용자의 단일 거대 월드를 처리하지 않는다.
- 각각의 개인 또는 호스트 월드가 독립적으로 존재한다.
- 공개 서버에도 최대 참가 인원을 설정한다.

핵심 감정:

"이 세계는 내 세계이며, 내가 파괴하고 설치하고 고친 흔적이 다음 접속에도 남아 있다. 친구가 참가하면 같은 세계에서 함께 살아가며 새로운 흔적을 남긴다."


2. 우선순위 점수 시스템 제거
----------------------------

기존 설계에서는 여러 플레이어가 서로 다른 출격 인스턴스에서 동일한 영구 월드 상태를 수정하고, 나중에 결과를 병합하는 구조를 고려했다. 이 경우 문 파괴와 수리처럼 서로 충돌하는 결과 중 하나를 선택하기 위해 공정성 점수가 필요했다.

개정된 구조에서는 다음 이유로 점수 시스템이 필요하지 않다.

- 한 월드에는 동시에 하나의 권한 서버만 존재한다.
- 월드에 접속한 모든 플레이어는 같은 실시간 게임 상태를 본다.
- 문이 파괴되거나 수리되는 순간 서버가 즉시 최종 상태를 결정한다.
- 서로 다른 월드의 결과를 하나로 합치지 않는다.
- 각 호스트 월드는 독립적으로 저장된다.
- 싱글플레이에서는 애초에 다른 플레이어와 변경 요청이 충돌하지 않는다.

따라서 다음 항목은 제거한다.

- 플레이어별 공정성 점수
- 승리 시 점수 감소
- 패배 시 점수 증가
- 연속 승리 패널티
- 연속 패배 보너스
- 서로 다른 출격 결과의 우선순위 병합
- 충돌 승자와 패자 판정

단, 멀티플레이에서 두 플레이어가 같은 아이템을 동시에 줍거나 같은 문을 동시에 조작하는 상황은 여전히 발생할 수 있다. 이것은 공정성 점수로 해결하는 문제가 아니라 권한 서버가 원자적으로 한 요청을 먼저 처리하는 일반적인 실시간 네트워크 문제다.


3. 게임 플레이 흐름
-------------------

3.1 최초 시작

- 새 게임 생성
- 개인 월드 ID 발급
- 초기 맵 상태 생성
- 개인 기지 생성
- 기본 장비와 퀘스트 설정

3.2 기지

- 장비 선택
- 창고 관리
- 제작
- 연구
- 홈 시설 건설과 업그레이드
- 월드 상태와 보스 정보 확인
- 싱글 출격 또는 멀티 방 개설

3.3 출격

- 하나의 연결된 맵으로 이동
- 파밍과 전투
- 주요 문과 벽 파괴
- 지뢰 및 방어 시설 설치
- 발전기나 경보 장치 조작
- 보스 추적과 전투
- NPC 수리 지원 또는 방해
- 자원을 가지고 기지로 귀환

3.4 귀환과 저장

- 획득 아이템 저장
- 사망 시 손실 처리
- 연구 및 퀘스트 진행 저장
- 맵의 중요 상태 저장
- 보스 상태 저장
- NPC 복구 작업 저장


4. 개인 영구 월드에 저장되는 상태
---------------------------------

개인 데이터:

- 플레이어 장비
- 개인 창고
- 재화
- 연구 진행도
- 제작법
- 홈 시설과 업그레이드
- 퀘스트 진행도
- 전적

월드 데이터:

- 주요 문과 벽의 파괴 상태
- 발전기 상태
- 경보 장치 상태
- 방어 시설 상태
- 플레이어가 설치한 지뢰
- 중요한 상자와 저장고 상태
- 보스 현재 체력
- 보스 부상 및 파괴된 부위
- 보스 치료 상태
- NPC 생존 및 작업 상태
- NPC 수리 시작과 완료 예정 시각
- 지역 위험도와 오염도
- 시간과 날씨

영구 저장하지 않는 상태:

- 탄피
- 작은 파편
- 일반 적의 모든 시체
- 순간적인 이펙트
- 중요하지 않은 소품의 파괴
- 일반 상자의 사소한 배치 상태

모든 것을 저장하면 데이터가 불필요하게 커지고 월드가 정리되지 않는다. 다음 플레이에 실제 영향을 주는 중요한 상태만 저장한다.


5. 하나의 맵을 계속 사용하는 방식
--------------------------------

맵 에셋은 하나만 제작한다. 그러나 같은 맵이라도 저장된 월드 상태에 따라 플레이 경험이 달라진다.

변화를 만드는 요소:

- 열려 있거나 파괴된 통로
- 지뢰가 설치된 길
- 작동하거나 멈춘 발전기
- 조명이 켜진 지하 시설
- NPC가 수리 중인 건물
- 보스의 현재 위치와 부상 상태
- 세력별 점령 구역
- 날씨와 오염
- 플레이어가 이전에 남긴 보급품

맵을 여러 개 제작하지 않아도 월드 상태 변화로 동선을 바꿀 수 있다.

예시:

1일 차:
- 동쪽 문이 잠겨 있음
- 중앙 발전기가 고장
- 보스 체력 100%

2일 차:
- 플레이어가 동쪽 문 폭파
- 발전기 수리
- 보스 체력 62%

3일 차:
- NPC가 동쪽 문 수리 중
- 발전기 덕분에 지하 연구소 개방
- 보스가 의료 시설에서 75%까지 회복

같은 지형을 사용하지만 접근 가능한 길과 위험 요소가 계속 바뀐다.


6. 싱글플레이 1차 개발 구조
---------------------------

첫 번째 버전에서는 플레이어 한 명과 개인 월드 하나만 구현한다.

권장 구조:

- 로컬 게임이 서버 역할과 클라이언트 역할을 함께 수행
- 게임 규칙은 서버 로직 계층에서 판정
- 화면, 입력, UI는 클라이언트 계층에서 처리
- 저장 데이터는 서버 상태를 기준으로 생성

싱글플레이 단계에서도 서버와 클라이언트 역할을 코드상 분리하는 이유:

- 나중에 멀티플레이를 추가하기 쉽다.
- 클라이언트가 체력과 보상을 직접 변경하는 구조를 피할 수 있다.
- 전투와 월드 상태의 최종 권한 위치가 명확해진다.
- 전용 서버로 전환할 때 게임 규칙을 다시 작성할 필요가 줄어든다.

잘못된 예:

- UI 코드가 인벤토리 저장 파일을 직접 수정
- 클라이언트 공격 애니메이션이 보스 체력을 직접 감소
- 지뢰 프리팹이 자기 판단으로 월드 저장 목록에 등록

권장 예:

- 클라이언트가 공격 요청 생성
- 서버 로직이 거리, 무기, 쿨타임, 피격을 판정
- 서버 로직이 보스 체력 변경
- 변경 이벤트를 화면과 UI에 전달
- 서버 상태를 저장 시스템이 기록


7. 멀티플레이 추가 후 구조
--------------------------

7.1 친구 초대형 멀티

- 월드 소유자가 방을 연다.
- 소유자의 실행 프로그램이 호스트 서버 역할을 한다.
- 참가자는 초대 코드나 친구 목록으로 접속한다.
- 모든 참가자는 호스트가 가진 하나의 월드 상태를 공유한다.
- 월드 변화는 호스트 기준으로 저장된다.
- 참가자의 개인 장비와 보상은 참가자 계정에 별도로 저장된다.

7.2 공개 서버형 멀티

- 월드 소유자가 공개 여부를 선택한다.
- 서버 목록에 월드 이름, 지역, 핑, 인원, 난이도를 표시한다.
- 최대 참가 인원을 제한한다.
- 권장 초기 인원은 호스트 포함 2~4명이다.
- 입장 권한, 비밀번호, 차단 목록을 제공한다.
- 월드 소유자가 저장과 운영 규칙을 정한다.

7.3 독립 월드 구조

월드 A:
- 소유자 A
- 참가자 B, C
- 파괴된 동쪽 문
- 보스 체력 40%

월드 D:
- 소유자 D
- 참가자 E
- 동쪽 문 정상
- 보스 체력 90%

두 월드는 같은 맵 에셋을 사용하지만 저장 데이터가 다르다. 월드 A의 변화는 월드 D에 영향을 주지 않는다.


8. 대규모 중앙 서버가 필요하지 않은 이유와 한계
----------------------------------------------

이 구조는 모든 플레이어를 하나의 월드에 넣는 MMO 방식이 아니다. 작은 독립 월드가 매우 많이 존재하는 구조다.

장점:

- 한 월드의 동시접속 인원이 적다.
- 월드끼리 상태를 동기화할 필요가 없다.
- 하나의 거대한 월드 시뮬레이션이 필요 없다.
- 서버 부하가 각 호스트 또는 인스턴스에 분산된다.
- 같은 맵 에셋을 모든 월드가 재사용한다.
- 월드 상태 충돌 병합이 사라진다.
- 친구 중심 협동과 개인 진행을 함께 제공할 수 있다.

주의할 점:

- 월드 수가 많아도 계정, 서버 목록, 인증, 저장 백업 서비스는 중앙 인프라가 필요할 수 있다.
- 플레이어 호스트 방식에서는 호스트 컴퓨터 성능과 네트워크 품질에 영향을 받는다.
- 호스트가 종료하면 일반적으로 방도 종료된다.
- 호스트 저장 파일을 로컬에만 두면 조작 가능성이 있다.
- 공개 서버를 24시간 운영하려면 전용 서버 또는 상시 호스팅이 필요하다.
- "초 다중접속"을 하나의 월드에서 처리하는 것은 아니며, 소규모 월드를 많이 분산 운영하는 방식이다.

따라서 정확한 설명은 다음과 같다.

"대규모 단일 월드를 운영하지 않고, 인원 제한이 있는 독립 영구 월드를 여러 개 운영해 전체 이용자 증가에 대응한다."


9. 권한 서버 원칙
-----------------

멀티플레이에서는 호스트 또는 전용 서버가 월드의 최종 권한을 가진다.

서버가 판정할 항목:

- 플레이어 이동 가능 여부
- 공격과 피해량
- 몬스터 및 보스 AI
- 아이템 생성
- 아이템 획득
- 문 파괴와 수리
- 지뢰 설치와 폭발
- 발전기 작동
- 보상 지급
- 월드 상태 저장

클라이언트는 행동을 요청한다.

예시:

- "아이템을 획득했다"가 아니라 "이 아이템 획득을 시도한다"
- "보스에게 500 피해를 줬다"가 아니라 "이 무기로 이 시각에 공격했다"
- "문이 파괴됐다"가 아니라 "이 폭발물을 사용해 문 폭파를 시도한다"

서버는 위치, 거리, 장비, 쿨타임, 대상 상태를 확인한 후 결과를 확정한다.


10. 실시간 동시 행동 처리
-------------------------

우선순위 점수는 제거하지만 멀티플레이 중 동시에 같은 대상에 상호작용하는 상황은 처리해야 한다.

예시 1: 같은 아이템 동시 획득

- B와 C가 같은 아이템을 거의 동시에 획득 요청
- 서버가 먼저 유효하게 도착한 요청을 원자적으로 처리
- 아이템 상태를 Available에서 Claimed로 변경
- 이후 요청은 이미 획득된 아이템으로 거부
- 두 명에게 동시에 지급되지 않도록 트랜잭션 또는 잠금 사용

예시 2: 문 수리와 폭파 동시 요청

- 서버의 한 틱에서 처리 순서를 결정
- 먼저 처리된 행동으로 문 상태와 버전 변경
- 다음 요청은 변경된 최신 상태를 기준으로 다시 검증
- 폭파 중인 문은 수리 불가, 수리 중인 문은 폭파 가능 등 명시적 게임 규칙 적용

예시 3: 지뢰 동시 해체와 폭발

- 서버 시각을 기준으로 사건 순서 확정
- 폭발 조건이 먼저 충족되면 폭발
- 해체 완료가 먼저 확정되면 지뢰 비활성화
- 클라이언트 애니메이션 시간이 아니라 서버 판정을 사용

이것은 공정성 점수 문제가 아니라 실시간 서버의 사건 순서와 원자성 문제다.


11. 상태 버전 사용
------------------

점수 시스템이 없어도 오브젝트 버전은 유용하다.

문 상태 예시:

- ObjectId: Door-12
- State: Destroyed
- Version: 19
- LastChangedAt: 14:03
- LastChangedBy: Player-B

서버가 문 상태를 변경할 때마다 Version을 1 증가시킨다.

용도:

- 늦게 도착한 오래된 요청 거부
- 재접속한 클라이언트 상태 갱신
- 저장 중복 방지
- 서버 장애 후 복구 확인
- 디버깅과 변경 이력 확인

클라이언트가 버전 18의 문을 수리하려 했는데 서버 문이 이미 버전 19라면, 서버는 최신 상태를 다시 전송하고 현재 규칙에 따라 요청을 재검증한다.


12. 개인 월드와 참가자 개인 데이터 분리
---------------------------------------

월드 소유자 데이터:

- 맵 상태
- 주요 시설
- 보스 상태
- NPC 상태
- 월드 난이도와 설정
- 월드 설치물

각 참가자의 개인 데이터:

- 장비
- 창고
- 연구
- 개인 재화
- 퀘스트
- 획득 보상

친구 B가 소유자 A의 월드에 참가했을 때:

- B가 문을 폭파하면 A의 월드에 파괴 상태가 저장된다.
- B가 획득하고 탈출한 개인 아이템은 B의 창고에 저장된다.
- A의 개인 연구와 홈 업그레이드를 B가 임의로 변경할 수 없다.
- 공유 시설 변경 권한은 소유자가 설정한다.

권한 설정 예시:

- 방문자: 전투와 파밍만 가능
- 친구: 지뢰 설치와 시설 조작 가능
- 관리자: 건축, 수리, 중요 시설 변경 가능
- 소유자: 모든 권한과 저장 관리


13. 호스트 저장 조작 문제
-------------------------

개인 호스트가 월드를 만들면 서버 비용을 줄일 수 있지만, 저장 파일과 서버 권한을 호스트가 보유한다. 따라서 공개 경쟁이나 거래를 넣을 경우 조작 문제가 생길 수 있다.

선택 가능한 운영 방식:

A. 완전 개인 월드

- 저장을 로컬에 보관
- 모드와 치트 허용 가능
- 해당 월드의 보상은 개인 또는 비경쟁 용도로 한정
- 개발이 가장 단순함

B. 검증된 개인 월드

- 계정과 주요 보상을 중앙 서버에 저장
- 호스트는 실시간 시뮬레이션 담당
- 중앙 서버가 비정상 보상과 수치를 검증
- 친구 협동에 적합

C. 공식 공개 월드

- 전용 서버에서 실행
- 월드 저장도 서버가 관리
- 공식 경제와 전적에 반영
- 운영 비용이 가장 높지만 신뢰성이 높음

권장 단계:

- 초기 싱글플레이: 로컬 개인 월드
- 첫 멀티 버전: 친구 초대형 호스트 월드
- 이후 공개 멀티: 전용 서버 선택 지원
- 경쟁, 거래, 글로벌 랭킹을 추가할 때 중앙 검증 강화


14. 호스트 종료와 월드 유지
--------------------------

플레이어 호스트 방식에서는 호스트가 종료하면 참가자도 계속 플레이하기 어렵다.

초기 정책:

- 호스트 종료 전에 월드 저장
- 참가자에게 종료 예고
- 참가자의 개인 보상 정산
- 모든 참가자를 기지 또는 메뉴로 이동

향후 선택 사항:

- 호스트 이전
- 월드 저장 파일을 다른 신뢰된 플레이어에게 전달
- 클라우드에 월드 스냅샷 저장
- 전용 서버로 월드 이전
- 소유자가 없어도 일정 시간 유지되는 임시 서버

호스트 이전은 AI, 물리, 진행 중 이벤트 상태까지 넘겨야 하므로 초기 개발 범위에서는 제외하는 것이 안전하다.


15. 보스 영속 상태와 치료
-------------------------

각 개인 월드의 보스는 독립된 상태를 가진다.

저장 데이터:

- BossId
- CurrentHealth
- MaxHealth
- Phase
- InjuryStates
- CurrentLocation
- TreatmentFacilityState
- HealingRate
- LastCalculatedAt
- DeadAt
- RespawnAt

보스 회복 방식:

- 게임이 꺼져 있는 동안에도 치료가 진행될 수 있다.
- 서버 또는 로컬 저장 시각을 기준으로 경과 시간을 계산한다.
- 매초 체력을 저장하지 않는다.
- 마지막 계산 시각부터 현재 시각까지의 회복량을 한 번에 계산한다.

회복량 예시:

회복량 = 경과 시간 × 기본 회복률 × 치료 시설 배율 × 부상 배율

게임 플레이 연결:

- 의료 시설이 정상: 빠른 회복
- 의료 시설 파괴: 회복 정지 또는 감소
- 의료 NPC 생존: 치료 가능
- 치료 재료 고갈: 회복률 감소
- 특정 부위 파괴: 최대 체력 또는 행동 패턴 변화
- 보스가 치료 중이면 의료 시설 습격 가능

싱글플레이에서는 개인 월드의 보스만 변화한다. 멀티플레이에서는 같은 호스트 월드에 있는 모든 플레이어가 하나의 보스 상태를 실시간으로 공유한다.


16. NPC 수리와 살아 있는 맵
---------------------------

파괴된 맵을 영구 방치하지 않고 NPC가 복구한다.

예시:

- 14:00 문 파괴
- 14:20 수리 NPC 도착
- 14:20~15:00 수리 진행
- 15:00 수리 완료

저장할 값:

- RepairStartAt
- RepairCompleteAt
- RepairState
- RepairNpcState
- RequiredMaterials
- InterruptionCount

게임이 실행되지 않는 동안에는 NPC를 실제로 시뮬레이션하지 않는다. 다음 접속 시 저장 시각과 현재 시각의 차이로 결과를 계산한다.

플레이어 행동:

- 수리 NPC 제거
- 수리 재료 약탈
- 재료 지원
- 주변 적 제거
- 발전기 복구
- 수리 시설 파괴

이 시스템으로 하나의 맵도 계속 변화하는 것처럼 만들 수 있다.


17. 지뢰와 설치물
-----------------

지뢰는 개인 월드에 영구 흔적을 만드는 핵심 요소다.

제한 규칙:

- 월드당 활성 지뢰 최대 수량
- 플레이어당 설치 수량 제한
- 기지와 생성 지점 설치 금지
- 중요 NPC 주변 설치 금지
- 일정 시간이 지나면 고장
- NPC 제거반이 해체 가능
- 날씨에 따라 수명 감소 가능
- 멀티플레이에서는 호스트 서버가 설치와 폭발 판정

저장 데이터:

- MineId
- WorldId
- OwnerPlayerId
- Position
- Rotation
- MineType
- InstalledAt
- ExpiresAt
- State
- Version

멀티플레이 참가자가 설치한 지뢰가 호스트 월드에 남는지는 소유자 설정으로 결정할 수 있다.

19. 저장 안정성
---------------

중요한 변경은 저장 도중 게임이 종료되어도 파일이 손상되지 않아야 한다.

권장 방식:

- 임시 저장본 생성
- 데이터 검증
- 이전 저장본 백업
- 새 저장본을 원자적으로 교체
- SaveVersion으로 마이그레이션 지원
- 일정 간격 자동 저장
- 중요 사건 즉시 저장

즉시 저장 후보:

- 출격 종료
- 보스 처치
- 주요 시설 파괴
- 홈 업그레이드 완료
- 멀티 호스트 정상 종료

매 프레임 저장하지 않고 변경 사항을 메모리에 유지한 뒤 안전한 시점에 묶어서 저장한다.


20. 멀티 네트워크 동기화
------------------------

실시간 동기화 대상:

- 플레이어 위치와 회전
- 플레이어 애니메이션
- 체력과 상태 이상
- 공격과 피격 결과
- 몬스터와 보스 AI
- 문과 시설 상태
- 지뢰와 설치물
- 아이템 생성과 획득
- 게임 시간과 날씨

권장 처리:

- 로컬 플레이어 이동은 예측 적용
- 서버가 실제 이동을 검증
- 오차가 나면 서버 위치로 조정
- 다른 플레이어는 보간으로 표시
- 피해와 아이템은 서버 응답 후 확정
- 중요 상태는 신뢰성 있는 전송 사용
- 위치처럼 자주 변하는 값은 최신 상태 중심으로 전송


21. 재접속 처리
---------------

- 참가자가 연결 해제되면 일정 시간 캐릭터 유지
- 재접속 토큰으로 같은 월드에 복귀
- 현재 월드 상태 스냅샷 재수신
- 오브젝트 버전 비교
- 누락된 중요 변경 재전송
- 이미 획득한 아이템 중복 지급 방지
- 호스트가 종료했으면 보상 정산 후 메뉴 이동


22. 싱글에서 멀티로 확장하기 위한 코드 원칙
-----------------------------------------

1. 게임 규칙과 화면 표현 분리

- 보스 체력 계산은 게임 규칙 계층
- 체력바 표시는 UI 계층

2. 저장 데이터와 씬 오브젝트 분리

- 씬 오브젝트 자체를 무작정 직렬화하지 않음
- 고유 ObjectId와 상태 데이터만 저장

3. 모든 중요한 행동을 명령 형태로 구성

- AttackCommand
- PickupCommand
- PlaceMineCommand
- DestroyDoorCommand
- RepairFacilityCommand

4. 서버 시각 기준 사용

- 쿨타임
- 보스 치료
- NPC 수리
- 설치물 만료

5. 결정적이지 않은 물리 결과를 그대로 저장하지 않음

- 중요한 결과만 서버가 확정하여 저장

6. 싱글에서도 서버 권한 흐름 유지

- 현재는 같은 프로세스 안에서 호출하더라도 나중에 네트워크 메시지로 교체할 수 있게 구성

25. 포트폴리오 강조점
---------------------

프로젝트 소개 문구:

"하나의 맵을 반복해서 사용하는 3D PvE 익스트랙션 게임으로, 플레이어마다 독립된 영구 월드를 보유합니다. 플레이어가 파괴한 문, 설치한 지뢰, 작동시킨 시설과 보스의 부상 상태가 다음 접속에도 유지되며, NPC 수리와 보스 치료가 실제 경과 시간에 따라 진행되어 하나의 맵이 계속 변화합니다. 싱글플레이 단계부터 게임 규칙과 클라이언트 표현을 분리하고 서버 권한형 명령 구조를 적용해, 추후 월드 소유자가 호스트가 되고 제한된 인원의 친구 또는 공개 참가자가 같은 실시간 월드를 공유할 수 있도록 설계했습니다."

기술적으로 보여줄 내용:

- 하나의 맵과 여러 독립 월드 저장 구조
- 월드 오브젝트 고유 ID
- 상태 버전 관리
- 게임 종료 후 시간 경과 계산
- 보스 체력과 치료 영속성
- NPC 수리 일정
- 지뢰 수량 및 만료 관리
- 서버 권한 행동 검증
- 동시에 같은 아이템을 획득할 때의 원자적 처리
- 호스트 월드와 참가자 개인 보상의 분리
- 서버 재시작 및 저장 복구

시연 영상 예시:

1. 문을 폭파하고 지뢰 설치
2. 게임 저장 후 종료
3. 다시 실행했을 때 문과 지뢰 유지
4. 시간이 지나 NPC가 문 수리
5. 보스에게 피해를 주고 게임 종료
6. 다시 접속했을 때 보스가 치료로 일부 회복
7. 멀티 버전에서 친구가 호스트 월드 참가
8. 친구가 설치한 지뢰가 호스트 월드에 저장
9. 두 플레이어가 같은 아이템을 동시에 획득 시도
10. 서버가 한 요청만 확정해 중복 획득 방지


26. 최종 판단
-------------

이 구조에서는 우선순위 점수가 필요 없다.

그 이유는 각 플레이어 또는 호스트가 독립된 영구 월드 하나를 가지며, 멀티플레이 참가자도 동일한 실시간 서버 상태 안에서 행동하기 때문이다. 서로 다른 인스턴스의 결과를 나중에 합치지 않으므로 공정성 점수로 승자를 결정할 상황이 없다.

다만 멀티플레이에서 동시에 같은 오브젝트를 조작하는 문제는 남는다. 이는 다음 방식으로 해결한다.

- 하나의 권한 서버
- 서버 시각
- 요청 검증
- 원자적 상태 변경
- 오브젝트 버전
- 명확한 행동 우선 규칙

또한 이 방식은 하나의 거대한 MMO 월드를 만드는 것이 아니다. 인원 제한이 있는 작은 영구 월드를 플레이어별로 많이 만드는 방식이다. 그러므로 한 월드의 서버 부하는 작고 서로 독립적이지만, 공개 서버 목록, 인증, 클라우드 저장, 공식 경제를 운영하려면 별도의 중앙 서비스가 필요할 수 있다.


한 줄 요약
----------

플레이어마다 하나의 영구 월드를 소유하고, 싱글에서는 혼자 그 세계를 변화시키며, 멀티에서는 월드 소유자가 호스트가 되어 제한된 인원의 참가자와 같은 실시간 상태를 공유한다. 월드끼리 결과를 병합하지 않기 때문에 우선순위 점수는 제거하고, 동시 행동은 권한 서버의 원자적 판정과 상태 버전으로 처리한다.
